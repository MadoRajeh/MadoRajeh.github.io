How I build, and what I've learned the hard way.

None of this is methodology for its own sake. Every rule below exists because breaking it cost me something first — a wrong fix, a wiped sheet, a fortnight spent building against an approach that could never have worked.

Eight rules

The ones I actually follow

Look at the real rows before forming a theory

The first thing I do with a data problem is print the actual records — not a summary, not a sample, the rows. Almost every wrong fix I have shipped came from starting with a plausible explanation instead of the data. A theory that survives contact with the raw rows is worth building on; one that hasn't met them yet is a guess wearing a lab coat.

Read the documentation before probing the system

Sweeping an API to see what answers tells you what responds. It does not tell you what exists. On one integration the vendor's own docs listed endpoints my probe never found — including the ones holding the records that were missing from every export. Twenty minutes of reading would have saved a fortnight.

Fix the input before polishing the output

A dashboard cannot recover a fact that was never recorded. When the reporting looks wrong, the cause is usually upstream of the reporting, and the cheapest fix in the whole chain is often a one-page guide that changes how something gets typed in.

Build the check into the tool, not into someone's routine

If a system needs a person to run a script, remember a step, or watch for a failure, it will eventually not get done — and the failure will be silent. Whatever needs checking gets built into the thing itself, so the tool is responsible for its own correctness.

Never let it guess

Where a system doesn't know something — a missing clock-out, an ambiguous status, an empty API response — it flags it rather than filling in something plausible. A confident wrong number is far more expensive than an obvious gap, because nobody goes back and checks it.

Work on a copy, and keep the way back

Anything that restructures live data runs against a copy first. Scripts keep numbered rollback points named for what changed next, so recovering from a bad change is a file swap rather than an evening of archaeology.

Don't break the shape people already read

When automating something a team has used for years, the output stays exactly as it was. Trading three hours of manual assembly for weeks of everyone relearning where their number lives is not a win, however much better the new layout is.

Ship it, then fix it against real use

The attendance tracker took nineteen rounds of fixes — overnight shifts, rounding, missed clock-outs, absence tagging. None of those were findable at the design stage. Real use is the only honest test, so the goal is to get there early and keep a short loop afterwards.

What this looks like in practice

Same shape, every project

01

Understand the loss

What is actually going wrong, measured — not what everyone assumes is going wrong. This is where most of the value gets found, and it costs nothing but attention.

02

Fix the input

Clean data at the point it is created. A training guide or a validation rule beats any amount of cleverness applied downstream.

03

Automate the middle

Whatever a person does the same way every week becomes a scheduled job that repairs itself, guards against bad writes, and keeps a way back.

04

Make the output obvious

One number that decides something, shown so plainly that nobody needs a walkthrough. Then get out of the way.

Worth saying plainly: I am not a computer science graduate. I started in data analysis, kept getting handed the next adjacent problem, and learned to build because the alternative was doing the same manual job forever. Every rule on this page was paid for.
