The self-repairing CRM sync

The system that quietly removed five hours a week, and the one I'd point at first if someone asked what I actually do.

The problem

A person was the integration

Every week somebody logged into the CRM, exported a file, opened it, cleaned it, pasted it into the reporting sheet and fixed whatever broke. Every report downstream was only as fresh as the last time a human remembered. Worse, the CRM's own exports quietly omitted a category of leads, so the numbers everyone trusted had a hole in them.

The engineering

The decisions that actually mattered

Read the vendor's documentation before probing the API

I initially swept the API for endpoints and built against what answered. The docs listed endpoints the sweep never found — including the ones holding the records the exports were missing. The lesson stuck: probing tells you what responds, documentation tells you what exists.

Strict mirror, not append-only

Early versions only ever added rows, so anything deleted upstream lived on forever and inflated every count. The sync now reconciles all three cases — new, changed and gone — and the sheet is a true mirror rather than an archive of everything that was ever true.

A guard so a bad pull can't wipe the sheet

If the API returns empty or wildly short, that is far more likely to be an outage than an evacuated CRM. The sync refuses the write and leaves yesterday's good data in place. Stale data you can spot beats an empty sheet you can't recover.

Versioned rollback points, kept deliberately

Eight numbered snapshots of the script sit alongside it, each named for what changed next. When a change misbehaves, recovery is a file swap rather than an evening of archaeology.

It repairs itself instead of raising a ticket

Transient failures retry with backoff. Recoverable problems get fixed in place. Only something genuinely novel surfaces to a human. Automation that needs babysitting has just moved the work, not removed it.
